# 两个改进循环：产出循环与改进循环（D-035 提议）

> 目的：课程、单元题、简答题批改……所有"由模型产出、要检验才能用"的东西，共用**一台**"产出 → 检验 → 定点修复"的机器；
> 在它之上，再用**另一台**机器改进产出者本身（递归自我改进，RSI）。两台机器的时间尺度、改动对象、裁判都不同，不能混在一起。

## 1. 今天暴露的问题

Git 课程跑了 4 轮，每一轮导师都去**改 prompt**（改进产出者），再**整份重新生成**（重做产出物）。结果：

- 每一轮修好上一轮的问题，又冒出新的问题——因为整份重生成，原本对的小节也被重写了。
- 一个产出物的问题，被当成"产出者"的问题去修：花了 4 次 prompt 迭代，却只是为了让一份课程能用。
- 每一步都要导师在对话里转，循环不会自己转。

根因不只是"生成模型弱"，而是**两个循环没分开，检验结果也没有指向产出物的具体位置**。

## 2. 两个循环

```
                        ┌──────────────────── 改进循环（外层，按天/周）────────────────────┐
                        │  对象：产出者的版本（Variant：prompt 部件、上下文配方、工具、模型） │
                        │  信号：很多次产出里反复出现的发现 + 学习结果                         │
                        │  动作：一次只改一层的改动提议 → 在用例集上做实验 → 留出集不变差才采纳 │
                        └──────────────────────────────┬─────────────────────────────────────┘
                                                       │ 采纳后，产出循环用新版本
┌────────────────────────── 产出循环（内层，按分钟）──────▼────────────────────────────────────┐
│ 输入 ─▶ 生成 ─▶ 检验（便宜的先跑）─┬─ 没有阻断 ─▶ 发布闸门 ─▶ 学习者用 ─▶ 学习结果（最终裁判）│
│                 ▲                 │                                                        │
│                 └── 定点修复 ◀─────┘ 有阻断且还有预算（最多 3 轮 / $1）                         │
│                    （只重写被指出的部分）  超出预算 ─▶ 需要你决定                                  │
└───────────────────────────────────────────────────────────────────────────────────────────┘
```

| | 产出循环（内层） | 改进循环（外层，RSI） |
|---|---|---|
| 改的是什么 | 这一份产出物（一份课程计划、一套题、一次批改） | 产出者本身（Variant 的某一层） |
| 多久转一次 | 每次产出，几分钟 | 攒够证据之后，几天 |
| 靠什么判断 | 检验器给出的**发现**（本次） | 很多次产出的发现统计 + 学习结果（跨次） |
| 谁来做 | 系统自动（生成者 + 检验器） | 优化者提议（先由导师兼任），学习者批准评测标准的改动 |
| 成功的定义 | 这一份通过发布闸门 | 在留出集上，"到达可发布的代价"更低，学习结果不变差 |

## 3. 产出循环：一台机器，多种产出物

和检验器的设计一样（D-001：一个模型，多种界面），**机器只有一台，产出物的种类是注册进去的**。每一种产出物定义五样东西：

| 定义 | 含义 | 课程计划 | 单元题 | 简答题批改 |
|---|---|---|---|---|
| 结构 | 产出物的 schema，**每一部分有地址** | `/sections/4/checkpoint/1` | `/questions/q6` | `/answers/q7` |
| 生成者 | 一个 Variant（带工具的 agent，或一次模型调用） | tutor-prep | （新）quiz-maker | short-grader |
| 检验器 | 按成本从低到高排的一串 | schema / plan_check → 命令安全审查 → lab verify → 评审模型 | schema / 答案不泄漏 / kg check → pytest 先红后绿 → 评审模型 | 格式 → 与 rubric 一致性 → 导师抽查 |
| 修复方式 | 拿到发现后，重写哪些部分 | 只重写被指出的小节 | 只重写被指出的题 | 重批被指出的那一题 |
| 发布闸门 | 什么情况下可以给学习者 | 没有阻断级发现 | 同左 | 同左；导师抽查可覆盖 |

### 发现（Finding）：检验器和生成者之间唯一的"货币"

```
Finding
  address    产出物里的位置（JSON Pointer），如 /sections/4/checkpoint/1
  severity   block（不修不能发布）| warn（记下，不阻断）
  evaluator  哪个检验器、哪个版本给的
  what       问题是什么（给生成者看的，要能照着改）
  evidence   证据：lab verify 的输出、页面原文、测试报错
  layer?     猜测根因在哪一层（prompt / context / tools / model）——给改进循环用，不给生成者用
```

有了地址，修复才能是"定点"的：修复时把**被指出的部分 + 对应的发现**交给生成者，其余部分冻结；
检验器再检查一次"没被指出的部分有没有被改动"，防止修一处、坏一处。

### 检验器的顺序（便宜的先跑，前面阻断就不跑后面的）

1. **静态检查**（确定性、免费）：schema、plan_check、答案不泄漏、知识节点存在。
2. **安全审查**（一次模型调用）：会被执行的命令先读一遍；加固定规则拦截 `rm -rf /`、`curl | sh`、练习场外的路径。只有这一步放行，才进下一步。
3. **环境实跑**（确定性、要时间）：lab verify、pytest 先红后绿。这是"环境给出的事实"，最可信。
4. **评审模型**（一次模型调用，按 rubric）：讲得清不清、题干和答案是否一致、有没有绕过要练的技能。
5. **学习结果**（延迟到学习者用过之后）：检查点一次通过率、费劲程度、单元题得分。**最终裁判**，只进改进循环。

每一个检验器的每一次结论都是一条 Grade（D-022 已有），发现挂在 Grade 上；每一轮修复是一次新的 Run，用 `caused_by` 连到上一轮的发现——整条链可以回放。

## 4. 改进循环（RSI）

产出循环自动转起来以后，会自然产生改进循环需要的数据：

- **反复出现的发现** = 产出者的弱点。例：今天"动手步骤就是检查点答案"在 4 轮里出现 2 次 → 一条改动提议的候选。
- **到达可发布的代价** = 产出者好不好的可自动测量的指标：平均修复几轮、花多少钱、多少次停在"需要你决定"。
- **学习结果** = 检验器准不准：评审模型打 5 分、学习者却卡住的，说明**检验器**要改（这是评测标准的改动，要学习者批准，D-022）。

改进循环的步骤就是 D-022 早已定好、还没建的那四样：

1. **ChangeProposal**：从统计里挑一个问题，只改一层（prompt 的一个部件 / 上下文配方 / 工具 / 模型）。
2. **Experiment**：在用例集（Dataset：开发集 + 留出集）上，新旧版本各跑 3 次产出循环。
3. **采纳**：留出集上"到达可发布的代价"不变差、阻断级发现不增加，才采纳；否则回滚。
4. **EvalChange**：改检验器（rubric、用例、评审 prompt）单独走，学习者批准。**优化者不能改卷**。

"换更强的生成模型"就是一条模型层的 ChangeProposal：用实验回答，而不是凭一次印象。
另外要注意：生成者和评审模型如果是同一个模型，评审会偏向自己的写法，评审最好用不同的模型或更强的模型。
