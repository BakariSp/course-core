## 0. 一句话结论

**学习体验这一半已经基本成型（Shell 课程"体感很好"）；系统自己转的那一半还没有——几乎每个"让流程往下走"的动作，都要导师（Claude Code）在对话里触发。**
下一阶段的目标不是加功能，而是把导师从运行时的流程里拿出去：导师只做"开发者的编码助手 + 抽查"，产品内部的出题、审阅、修复、发布、调整路线都由系统里的 agent 和检验器完成。

## 0.1 产品是什么、使用者怎么想（2026-09-27 学习者补充）

**一句话：这是一个为我量身定制课程的软件。** 教学决策由 LLM 承担，并且自动优化；用户只需要提要求、学。

**使用者是真正的用户，不是开发者。** 他只关心自己学习要做的事，不会把自己当成调 prompt、看运行记录、决定"要不要重新备课"的人。他要看到的信息按重要程度排：

| 顺序 | 信息 | 回答的问题 | 举例 |
|---|---|---|---|
| 1 | **我的信息**（最重要） | 我是谁、我要什么；我学到哪了、会了什么、哪里弱、花了多少时间 | 目标和要求、下一步、掌握情况、学习记录 |
| 2 | **课程信息** | 系统给我排了什么：学什么、为什么是这个顺序、现在能不能学 | 路线（part → 单元）、每个单元的状态、这个单元为我调整了什么 |
| 3 | **系统信息** | 有哪些 agent，各自为了改进我的学习在做什么，刚刚做了什么，为什么这样做 | 备课、出题、批改、评审、调整检查 |

- **能挑战**：对这三类信息，用户都能说"不对"。比如"这个我其实会"（我的信息）、"这节讲得太跳"或"我想先学数据库"（课程信息）、"这道题批改得不对"（系统信息）。
  挑战是"提要求"的一种形式：它作为一条学习信号交给 agent 处理，处理结果对用户可见。用户**不需要**去改文件，也不需要自己做系统层面的决定（比如重新备课）。
- **不属于用户视角的东西**：文件路径、运行 id、prompt、检验轮次、"重新备课"这类流水线操作。它们都收进开发者视图（§4.3），另开一个入口。
- MVP 先用后端 core 已有的数据来做；但判断界面好不好的标准，是用户的心理模型，不是后端有什么数据。

### 0.1.1 页面设计原则（2026-09-27，F-069）

**标题是导航标签，不是说明。** 学习者带着一个词来找东西（"大纲""先修""进度"），标题就得是这个词，不用再翻译一次。

| 规则 | 反例 | 正例 |
|---|---|---|
| 标题是名词或概念，不写句子、不写问题 | "学什么""为你做的调整" | 大纲、先修要求 |
| 标题下面不放解释性小字；确实需要的解释收进「?」或者展开后再看 | "备这一版时，系统读了你的这些信息" | （去掉） |
| 状态用形式表达（徽章、✓、数字），不写成句子 | "各节 7/7 学完 · 单元题 8 道，还没做" | `7/7 节` `单元题 0/8` |
| 一屏只有一个主按钮 | 每一行都有蓝色按钮 | 只有"继续学"是主按钮 |

**词表**：课程 · 继续学习 · 课程目录 · 待确认 · 课程设置 · 大纲 · 学习目标 · 我的进度 · 先修要求（已满足 / 不满足 / 本单元要学）· 版本 · 我的（知识点 / 学习记录 / 资料）· 老师的观察 · 老师 · 动态 · 为什么这样教 · 备课记录 · 我的反馈 · 费用。

**先建模再排版**：每一页都先列出学习者来这里要做的事，按频率排序，再按频率分四级：
- **一级**：打开就能看到，一眼能读。
- **二级**：在页面上，只占一行，点开才看细节。
- **收起**：放在折叠块里。
- **别处**：挪到另一个页面。

每一页的分层表在 D-046 的「修订（F-069）」里。

## 0.2 场景分析：三个维度 × 最小闭环（2026-09-27，F-068）

### 维度

| 维度 | 取值 |
|---|---|
| **对象** | 课程：课程清单（学什么、主课、目标）· 路线（单元和顺序）· 单元 · 小节 · 检查点 · 练习场 · 单元题 · 课程版本 · 插入物<br>我：画像 / 目标 / 要求 · 学习证据 · 掌握情况和薄弱点 · 学习时间<br>系统：agent（调研、备课、评审、练习场验证、出题、批改、调整检查、课程评测）· 任务（在跑 / 排队 / 失败）· 每次运行的结论、原因、花费 |

### 透明性：四环链路

agent 系统的透明性，看每一条"我的信息"能不能走完四环：**我有这条信息 → 哪个 agent 读了它 → 它影响了课程的哪里 → 我能挑战**。

| 我的信息 | 谁在用 | 影响 | 能看到吗 | 能挑战吗 |
|---|---|---|---|---|
| 画像（`learner.md`） | 备课 | 讲法、例子 | 只在开发者视图 | 📄 |
| 单元要求（syllabus 的 notes） | 备课 | 这个单元的重点 | 只在开发者视图 | 📄 |
| 已掌握 | 备课 | 哪些词跳过、一句带过 | 只在开发者视图 | 部分能 |
| 薄弱点 | 备课、出题 | 放慢讲、出变体题 | 只在开发者视图 | ⌨ |
| 单元内的表现 | 出题 | 出什么题 | ❌ | ❌ |
| 时间预算 | 备课 | 节数和时长 | ❌ | 📄 |

第三环"影响了哪里"目前没有任何记录：agent 需要在产出里写明依据（新的产出字段）。

### 最小闭环：单元的状态和流转

一个单元有两条状态线：**内容线**（备课、出题）和**学习线**（检查点、单元题）。

```
内容线：没备课 ──▶ 备课中 ──通过──▶ 能学 ──再备一次──▶ 有新版本 ──换──▶ 能学
                     ├──3 轮 / $1 用完──▶ 检验没通过
                     └──出错 / 中断──▶ 没走完
学习线：能学 ─▶ 在学 k/n ─▶ 各节通过 ─▶ 单元题（出题中 / 出好 / 出题失败）─▶ 交卷批改 ─▶ 学完 ─▶ 下一单元
```

| 流转 | 现在谁触发 | 应该谁决定 | 现在的出路 | 断在哪 |
|---|---|---|---|---|
| 没备课 → 备课中 | 用户按钮；自动预备只备"下一个、从没备过的" | 系统：路线定了就按顺序备 | — | 自动预备看不见；22 个"备课"按钮暗示要用户来点 |
| 备课中 → 没走完 | 出错 / 进程中断 | 系统 | 只有"重新备课" | 命令行能续跑（`prepare --from`），网页没有；故障本该系统自己续跑 |
| 备课中 → 检验没通过 | 3 轮 / $1 用完 | 不该是学习者 | 只有"重新备课"；原因在开发者面板 | 同样的 prompt 重来多半还卡在同一处；学习者判断不了、也改变不了 |
| 能学 → 有新版本 | 只有用户手动重新备课 | 修不修由系统定；换不换按"对进度的影响"问学习者（D-044） | "换成新版本" | 看不到改了什么 |
| 出题失败 | — | 系统 | "重新出题"按钮交给用户 | 同备课失败 |
| 交卷 → 学完 | 由证据算出；但 syllabus 的 `status` 还是手写的 | 由证据算出 | — | 两个来源不一致 |
| 学完 → 掌握了什么 → 下一单元 | — | 系统给出结论和推荐 | ❌ | 闭环最后一步断了 |

**结论**：后端状态是齐的。断在两处：① 失败状态的出口只有"重来"一个，而且交给了用户；② 学完之后没有出口。

### 原则一：失败按原因分，学习者只回答关于自己的问题

| 失败的原因 | 例子 | 谁决定 | 用户看到什么 |
|---|---|---|---|
| 临时故障 | 网络断、进程中断、限流 | 系统自动从断点续跑（有上限） | "准备中（中断过一次，已自动续上）" |
| 系统能力不够 | 检验 3 轮没过；prompt / 模型的问题 | 系统换一种策略再试一次（如换更强的模型），还不行就上报开发者 | "暂时不能学：〈一句人话的原因〉。已交给系统改进，你可以先学 X"。**没有"重来"按钮** |
| 缺学习者才有的信息 | 讲座太大要拆、范围不清、目标没说 | **学习者**，问题要问成他答得了的形式（系统先给提议） | "Kleppmann 讲座有 8 小时，系统提议拆成这几讲，你想重点学哪几讲？" |

学习者只回答关于**自己**的问题（目标、时间、偏好、会不会）；内容质量和怎么重试，由系统决定、开发者兜底。所有决定和原因都要能看见、能挑战。

### 原则二：透明性按四环衡量

每新增一种"我的信息"或一个 agent，都要回答四个问题：它存在哪、谁读它、它改变了课程的哪里、我在哪里能看到并挑战它。缺一环就是缺陷。

**14 个环节里，11 个要导师手动；最关键的"学习信号 → 下一单元"没有任何人做。**
这和 PRD_V1 的定义一致地指向同一个问题：CLAUDE.md 里的"导师"混了两个角色——

1. **开发者的编码助手**（Claude Code 改这个仓库）：应该保留。
2. **产品运行时的角色**（出题人、审阅人、发布人、路线规划人）：应该变成系统里的 agent / 检验器，而且每一个都有版本、有评测。

## 4. 想要的产品形态

### 4.1 角色

| 角色 | 是什么 | 做什么 |
|---|---|---|
| **学习者** | 人 | 定目标和课程清单；学；给信号；批准"评测标准"的改动和学过单元的新版本 |
| **系统里的 agent / 检验器** | 有版本、有评测的模型调用 | 规划路线、备课（大纲 → 分节）、出题、批改、审阅、修复、复习 |
| **开发者的编码助手（Claude Code）** | 仓库外部的开发工具 | 改代码、改 prompt 和评测、抽查 agent 的判断；**不在运行时的流程里** |

### 4.2 一个单元的生命周期（全程不需要导师）

```
curriculum 定好（学习者同意一次）──▶ 系统按顺序提前生成后面的单元：大纲 → 分节 → 产出循环 → 发布
                                   （不逐个单元给学习者看大纲；想改随时能改）
                              │
学习者学 C1，每学完一节 ──▶ 调整检查：这一节暴露的薄弱点，和后面已生成的单元（C2 …）有没有关系？
                              │        有 ──▶ 生成"插入物"：一段讲解 / 一道练习，插到 C2 的相关位置
                              │               （插入物也走产出循环；原有小节一个字不改）
                              ▼
学习者打开 C2 ──▶ 看到"和之前有关"：哪条插入物、因为 C1 的哪一处（原话 / 错题）
                              │
                     学习者：进入学习 → 检查点 → 单元题（系统出题、系统批改）
                              │
                     单元学完：自动跑课程评测 → 信号进学习者模型 → 统计进改进循环
```

### 4.2.1 调整 = 插入，不是重新生成（学习者 2026-09-26 确认）

| | 重新生成 | 插入（采用） |
|---|---|---|
| 改动范围 | 整个单元或整节 | 只新增一段讲解或一道练习，原有内容不动 |
| 花费 | 贵（一个单元一次 agent 运行） | 便宜（一次模型调用 + 检验） |
| 进度 | 按版本算的进度会断 | 原有小节不变，进度不断 |
| 可追溯 | 难看出改了什么 | 每条插入物记着"因为 C1 的哪条证据" |
| 和 D-035 的关系 | — | 插入物是一种新产出物；冻结检验天然成立（只加不改） |

- **什么时候检查**：C1 每一节检查点通过时（不是等整个单元学完）。检查本身是一次便宜的判断：这节的证据（错过的检查点、👎 的新词、费劲程度、提问）和后面单元的大纲有没有关系；大多数时候结论是"没关系"，不产生插入物。
- **插到哪**：只插到学习者**还没学过**的小节前面；已学过的小节不动。
- **学习者能改**：打开 C2 时能看到每条插入物和它的来由，可以删掉；也可以在"更多"里要求重新生成（保留，但不是默认路径）。
