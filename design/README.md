# 产品设计记录

这个学习环境按"边用边改"的方式演进：学习者在学的过程中说出体验，导师把它记成反馈，提出改动，改完再验证。
所有这些都留在这里，任何一次改动都能追溯到"是谁、在什么场景下、遇到了什么问题"。

```
学习者的体验 / 想法 ──► FEEDBACK.md（F-xxx，原话 + 场景；想法池，不限量、不用想清楚）
                              │  学习者决定要做
                              ▼
                        QUEUE.md（只放编号，从上到下是顺序，学习者排）
                              │  轮到它、在制品有空位
                              ▼
                        DECISIONS.md（D-xxx：问题、证据、选项、决定、理由、怎么验证）
                              │  状态只存在标题里（D-070）：
                              │  排队 → 需求评审 → 设计 → 开发 → 验证 → 已完成（另有"放弃"）
                              ▼
                        代码改动（一个 D-xxx 一个分支，--no-ff 合并，D-059）
                              │
                              ▼
                        验证：学习者再用一次，结果回写到 D-xxx 的「验证」一栏
```

| 阶段 | 出口条件（过闸） | 谁拍板 |
|---|---|---|
| 需求评审 | 问题陈述 + 验收例子（至少 1 个反例）+ 没回答的问题都答了 | 学习者 |
| 设计 | 改哪些模块、数据和状态有没有变（新字段、新开关、新表）、测试怎么写 | 学习者 |
| 开发 | 一个分支、测试全绿、`--no-ff` 合并，合并提交号写回「实现」 | 导师 / agent |
| 验证 | 学习者用过，结果写进「验证」 | 学习者 |

在制品上限：需求评审 1 件 + 设计/开发 1 件；验证不占名额，但超过 5 件时先回写验证。

## 规则

- **反馈记原话**，加上当时在做什么（哪个单元、哪道题、哪个页面）。不要先改写成解决方案。
- **一条决定要能回答五个问题**：解决什么问题、证据是哪几条反馈、考虑过哪些做法、为什么选这个、怎么判断改好了。
- 决定由学习者拍板；导师负责提出、实现和验证。新想法先查 DECISIONS 和 QUEUE 里是不是已经有了，有就并进去。
- 标题状态和实际对不上，就是 bug：做完合并当场改标题，不攒。
- 被放弃的决定不删，写清楚为什么放弃——以后遇到同样的问题时，这比成功的决定更有用。
- 两个文件都只追加，旧条目只更新「状态」和「验证」两栏。
