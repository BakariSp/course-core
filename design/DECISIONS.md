## D-001 检验器：一个模型，多种界面 · 已完成 · 2026-09-25

- **问题**：题型多样（选择、填空、代码、终端、简答），但判分、记录、掌握度计算不该每种题各写一套。
- **证据**：F-002、F-003
- **决定**：所有检验器实现同一个协议 `view()`（给页面的数据，不含答案）/ `act()`（作答中的交互，不记录）/ `check()`（判分 → Verdict）。记录和掌握度只依赖 Verdict。
- **理由**：新增题型只需要一个模型类 + 一个界面组件；判分之后的流程只有一份。
- **位置**：`studykit/checkers/`，`web/index.html` 的 `RENDERERS`

## D-002 答题记录只追加，进度页由它生成 · 已完成 · 2026-09-25

- **问题**：进度要人和 AI 都能看、都能维护，还要能推断掌握程度。
- **决定**：`attempts.jsonl` 只追加，是唯一证据；`syllabus.yaml` 人手改；`progress.md` 只由程序生成。
- **理由**：和 nanoteacher 的 `topic_memory.json` → `TOPIC_MEMORY.md` 同一个模式——两边都能写的派生文件迟早不一致。

## D-003 掌握度四级，看最近 3 次 · 已完成 · 2026-09-25

- **决定**：每道题标 1 记忆 / 2 理解 / 3 应用 / 4 分析；某一级最近 3 次平均 ≥ 70% 算通过；通过后 14 天没练标"需复习"。
- **理由**：规则简单到学习者自己能算，出题时直接知道下一步该练哪一级。

## D-004 代码题就地编辑，可以展开成全屏，带行号 · 已完成 · 2026-09-25

- **证据**：F-004、F-005、F-007
- **考虑过**：单独的编辑页面（被否：跳页面打断体验，F-007）。

## D-005 每次运行测试都记录 · 已完成 · 2026-09-25

- **证据**：F-006
- **决定**：每次「运行测试」和「提交」连同代码快照写进 `runs.jsonl`。不参与掌握度计算（掌握度只看提交），导师批改时用 `study.py runs` 看作答过程。
- **理由**：跑了 8 次才通过和一次通过，掌握程度不一样；这个差别只在过程里看得到。

## D-006 终端原样输出是权威，错误分组只是辅助 · 已完成 · 2026-09-25

- **证据**：F-008、F-009
- **决定**：结果面板两个标签，「终端输出」（pytest 原样输出，默认）在前，「错误分组」在后；同一种错误、同一处代码的测试合成一组，每个测试显示触发它的输入和各自的期望值。
- **理由**：整理过的信息可能整理错，原始输出不会；参照 Gradescope、PrairieLearn 等 autograder 的通行做法。

## D-007 课前讲解交给助教 agent，导师只改 prompt 和做评测 · 已完成 · 2026-09-25

- **证据**：F-010、F-011
- **决定**：视频课是主讲；助教 agent（`agents/tutor-prep`）查资料写课前指南；导师不直接写内容，只改 agent 的 prompt、环境和评测，审阅后发布。
- **理由**：内容生成可以反复迭代、可以评测、可以换模型；导师手写的内容做不到这些。

## D-008 agent 以最小权限运行在我们定义的环境里 · 已完成 · 2026-09-25

- **证据**：F-012
- **决定**：pi 当引擎，不改源码；runner 关闭 pi 的全部内置工具、用户配置和上下文文件，只开放环境工具（`fetch_url` 白名单抓取、`submit` 带检查的提交）。工具用 Python 实现，pi 那边只有一个薄适配器。
- **理由**：agent 能做什么完全由环境决定，可测试、可审计；换框架（或加 MCP）只需要换适配器。

## D-009 链接必须打开过；评分模型的质疑由程序核对 · 已完成 · 2026-09-25

- **问题**：第一版允许引用"页面上出现过的链接"，评分模型却要求"打开过"，标准不一致；评分模型看不到页面正文，曾把真实的版本号（pytest 9.1.1）误判为编造。
- **决定**：环境只接受打开过的页面；评分模型把怀疑的说法连同原文列出来，由程序到 agent 读过的页面里核对。
- **验证**：同一份 pytest 指南重新评测，5 条质疑全部核实为有出处，`grounded` 从 3 分变成 5 分。

## D-010 学习指南改成"课程页面"：分段、限时、有目标、直接接到练习 · 接受 · 2026-09-25

> 学习者拍板（2026-09-25）：每个单元上限 **3 小时**，每次学习 **45 分钟**；先做这一条，开源整理（D-011）等课程页稳定后再做。

- **问题**：现在的指南是"导航"，不是"课"。它让学习者自己去挨个看讲义和视频（F-013）；没有时间预算，一个单元可能学几个星期（F-014）；避坑写得泛，看不懂（F-013）。
- **证据**：F-013、F-014、F-015
- **考虑过**：
  1. 只改 prompt，让指南写得更具体。——不够：形式还是一篇长文，问题 F-014、F-015 解决不了。
  2. **agent 产出结构化的课程计划，网页渲染成课程页面**（推荐）。
  3. agent 把讲义全文翻译搬进来。——不做：版权上不合适，而且学习者要的是"带着学"，不是换个地方读原文。
- **决定（提议）**：
  - agent 不再交 Markdown，而是交一份**课程计划**（结构化数据，环境按 schema 校验）：
    ```
    单元 → 部分（part）→ 小节（section）
    每个小节：预计分钟数 · 目标（学完能做到什么）· 讲解（agent 用自己的话讲清楚，附原文出处）
             · 动手（要敲的命令 + 预期看到什么）· 常见坑（症状 → 原因 → 怎么办）· 对应的视频/讲义位置
    ```
  - **时间预算是硬约束**：整个单元和每个小节都有分钟数上限，超了 `submit` 直接退回。预算由学习者设定（见待定问题）。
  - 网页新增课程页：左边是 part / section 目录和进度，右边是当前小节；每个小节可以标记"学完"，页面顶部显示已用时间和剩余预算；最后一个小节连到这个单元的练习题。
  - 练习题（problem set）按各小节的"目标"来出，检验器和掌握度沿用现在的。
  - 评测跟着改：自动检查加上"时间预算""每个小节都有目标和动手步骤""每个坑都有症状/原因/怎么办"；rubric 加一条"新手看得懂"。
- **怎么验证**：学习者用新的 Shell 课程页学一遍，回答三个问题——有没有需要自己去翻原始材料才学得下去的地方？实际用时和预估差多少？哪一处看不懂？
- **待定（学习者决定）**：每个单元的时间上限、每次学习的时长。
- **实现（2026-09-25，第一版）**：
  - agent 改交结构化课程计划（`submit_plan`），环境按 schema 校验：总时长 ≤ 180、每节 ≤ 45、每节有目标/讲解/动手/出处、每个坑有现象/原因/怎么办、链接必须打开过。
  - 课程页 `/?unit=<单元>`：左侧目录（部分 → 小节，分钟数，✓），右侧当前小节；顶部显示计划和实际用时，明显超时会提醒；最后一页列出"学完能做到"并连到练习题。
  - 进度记在 `progress/study_log.jsonl`（只追加），实际用时只算页面在前台的时间，单节上限为计划的 3 倍。
  - 第一版 Shell 课程计划：3 部分 7 节 168 分钟，评分 4.67/5（`teaches` 5 分）。
- **验证**：「学完这一节」按钮已在真实使用中跑通（study_log 里第 1-3 节各有一条 done，2026-09-25）；但记录的用时只有 0.1/0.8/3.3 分钟，见 F-029 → D-016。三个问题待学习者学完后回答。已知在 F-018（没有 shell 基础）写进学习者画像之前生成，第二版要验证讲法是否跟得上。

## D-013 小节检查点：做对了才算"学完这一节" · 接受 · 2026-09-25

- **问题**：现在"学完这一节"是自己点的按钮，进度条量的是"看过"，不是"懂了"（F-025）；常见坑写在讲义里没人看（F-022）。
- **证据**：F-022、F-025
- **考虑过**：
  1. 每个单元学完再做一整套练习（现状）。——反馈来得太晚，第 2 节没懂，第 3-7 节都建立在误解上。
  2. **每节末尾 1-3 道检查点题，做对才打勾**（推荐）。
  3. 每段讲解后面都插题。——打断太多，一节 20 分钟被切成五段。
- **决定（提议）**：
  - 每节末尾放 1-3 道检查点题，沿用现有检验器（choice / fill / 练习场状态检查，见 D-014），不计入掌握度（掌握度仍然只看单元练习题）。
  - 进度条只数**做对了检查点**的小节；"学完这一节"按钮去掉。
  - 做错时按三级给提示：方向 → 关键概念 → 接近答案。**常见坑挪到这里**：agent 为每个坑写"哪种错误答案说明你踩了这个坑"，答错时才出现，而不是在讲义里列一排。
  - 下一节默认锁住；可以"先跳过"，跳过的小节在目录里显示为"看过未验证"（灰色），并记一条 `skip` 事件。
- **怎么验证**：学下一个单元时，看每节第一次就做对的比例。目标 60-85%：太高说明题太浅，太低说明讲解没讲清。另外问学习者：打勾的时候有没有"我确实会了"的感觉？
- **待定**：硬锁（必须做对）还是软锁（可以跳过但会标记）。
- **实现（2026-09-25）**：检查点的答案、提示、陷阱只在服务器上（`course.public_plan` 去掉），页面通过 `/api/unit/check`、`/api/unit/hint` 判分和要提示；进度条只数通过的小节；跳过记 `skip` 事件，目录里标 ◐，有练习场的节可以用参考做法补齐。已在浏览器里走通：答错 → 出现对应的坑 → 要提示 → 答对 → 整节通过 → 费劲程度 → 下一节。

## D-014 贯穿整个单元的"练习场"，终端放进课程页 · 接受 · 2026-09-25

- **问题**：学一节要在视频、课程页、Git Bash、终端输出之间来回切（F-020）；每节的动手步骤互不相关，做完就扔，上一节学的东西下一节用不上（F-026）；练习目录没有被强制，练 `sed -i` 改到了仓库里的真实文件（F-030）。
- **证据**：F-020、F-026、F-030
- **考虑过**：
  1. 继续让学习者自己开 Git Bash。——四个窗口，还会在错误的目录里练。
  2. 复用现在的练习终端。——它是模拟的，没有管道、`cd`、`grep`、`sed`，教不了 shell。
  3. **课程页里嵌一个真实的 bash（Git Bash 的 bash.exe），工作目录限定在练习场**（推荐）。每条命令用 `bash -c` 执行，服务器记住当前目录。管道、通配符、`sed`、`cd` 都是真的；Tab 补全、`vim`/`less` 这类交互程序不支持，这几处讲义会让学习者去 Git Bash 里试。
  4. 完整的伪终端（xterm.js + pywinpty + WebSocket）。——体验最好，但要加两个依赖，还要把服务器换掉（现在的服务器只用 Python 标准库）。等方案 3 不够用了再考虑。
- **决定（提议）**：
  - **每个单元一个练习场**：`sandbox/labs/<单元>/`，有一个故事主线。Shell 单元的主线：*nanoteacher 的测试服务器出了问题，你拿到一个乱糟糟的项目目录，要一步步查清楚*：
    | 节 | 任务（成为下一节的材料） |
    |---|---|
    | 1 | 确认自己在哪（`pwd`），建好工作区 |
    | 2 | 在目录树里找到 `logs/` 和 `config/` |
    | 3 | 查明服务用的是哪个 `python`（`which`、`$PATH`） |
    | 4 | 用 `grep` 在日志里找到 ERROR，定位出错的配置项 |
    | 5 | 用 `sed` 修好配置（先备份，先预览） |
    | 6 | 用管道统计每种错误出现几次，写进 `report.txt` |
    | 7 | 把 4-6 写成一个每天能跑的检查脚本 |
  - 每节开始前，环境把练习场存一个快照；有"还原到本节开始"按钮，改坏了不怕。
  - 检查点题（D-013）里有一种"检查练习场状态"的题：`report.txt` 里有没有正确的计数、配置改对没有，沿用终端检验器的 checks 写法。
  - 课程页布局：讲解在左，终端在右，视频链接带时间点。窗口从四个减到两个（视频 + 课程页）。
  - 成就感：目录上每节是一个"任务"，完成后显示你在练习场里留下了什么（例如"找到了 3 个 ERROR"），单元结束时是一份你自己跑出来的 `report.txt`。
- **安全**：真实 bash 能访问整台电脑，和自己打开 Git Bash 一样；服务器只监听 127.0.0.1。命令只在练习场里执行，但不做沙箱隔离——这是本机学习工具，不是多用户服务。
- **怎么验证**：学下一节时记录切换窗口的次数（学习者自报），问"还觉得来回切很累吗"。练习场外的文件不应该再被改动。
- **实现（2026-09-25）**：`studykit/lab.py`：每个单元一个常驻的 Git Bash（命令写进 cmd.sh 再 source，stdin 接 /dev/null），练习场默认在 `~/cs-study-lab/<单元>`；第一次打开某节时存快照，可以还原；离开练习场时提醒。`study.py lab verify` 在发布前把每节的动手命令和参考做法跑一遍（做之前不通过、做之后通过），发布前必须通过。

## D-015 课程页减噪：出处放到单元一级，常见坑不再单列 · 接受 · 2026-09-25

- **问题**：每节都重复列同一个讲义页面（F-021）；常见坑是噪音（F-022）。
- **证据**：F-021、F-022
- **决定（提议）**：出处和视频链接放到单元首页一次；每节只留一个"视频从 mm:ss 看到 mm:ss"（找得到时间点才写，找不到就写章节名）。常见坑合并进检查点的提示里（D-013）。schema 和评测同步改。
- **怎么验证**：学习者读一节时，页面上不再有学习者会跳过不看的区块。
- **实现（2026-09-25）**：schema v2 去掉每节的 `sources` 和 `pitfalls`（环境会退回），出处放在单元的 `sources`，坑变成检查点的 `traps`。旧版课程页上的坑收进「遇到问题时看」。

## D-016 学习时间：按"学习会话"记录，不只算页面在前台的时间 · 接受 · 2026-09-25

- **问题**：F-029 的数据说明现在的计时几乎没用：第 1-3 节计划 48 分钟，记下来 4.2 分钟。真实的学习发生在视频和终端里。也没有按天看的历史（F-027）。
- **证据**：F-027、F-029
- **考虑过**：
  1. 只算页面在前台的时间（现状）。——漏掉视频和终端。
  2. 手动开始/结束计时。——一定会忘记点结束。
  3. **打开课程页就开始一个会话，有活动就续上，没活动 15 分钟自动结束，结束时间回填到最后一次活动**（推荐）。活动包括：点开小节、在内置终端里敲命令、做检查点、点视频链接。课程页在后台（在看视频）也不中断，除非 15 分钟内一点活动都没有。
- **决定（提议）**：
  - 新事件：`session_start` / `session_end`（带开始、结束时间、学了哪些小节）、`activity`（心跳，1 分钟最多一条）。
  - `python study.py time` 按天输出：`2026-09-25 16:20–17:10 · Shell 第 1-3 节 · 50 分钟`，以及每天、每周合计。
  - 每节的实际用时 = 这节打开期间的会话时间，用来和计划比（D-019）。
  - 另外加一个"我在看视频"按钮：点一下在活动里标注这段时间在看视频（第 1 讲的 48 分钟可以事后补录一条）。
- **怎么验证**：学习者学一个晚上后，看 `study.py time` 的输出，和自己感觉的时间差不超过 10 分钟。
- **实现（2026-09-25）**：`studykit/timeline.py` 从 study_log、attempts、runs 三个日志的时间戳算会话（间隔 ≤ 15 分钟算同一次，每次收尾记 1 分钟），不存会话；课程页在有人操作时每分钟发一次心跳，「我在看视频」期间也发（最多 2 小时）。`study.py time` 按天输出，`time add` 补录。第一版的实际数据：16:20–16:58 记到 19 分钟（中间看视频超过 15 分钟没有心跳，所以断开了）。

## D-017 新词预测和认知负荷：让"讲得太难"可以被量出来 · 接受 · 2026-09-25

> 2026-09-25：D-020 已接受。新词就是知识图里的术语节点，已知词表是投影，不另建存储。

- **问题**：同一段内容，对没有 shell 基础的人和对程序员，难度完全不同（F-019、F-024）。现在 agent 写讲义时没有任何约束告诉它"这一节新东西太多了"，也不知道它对学习者的预测准不准（F-023）。
- **证据**：F-019、F-023、F-024，以及 F-018（glob/sed 那段跟不上）
- **考虑过**：
  1. 让 agent 自己给每节打一个 load 分。——模型的自评不可靠，也没法校准。
  2. **用可以数出来的东西算预测负荷，用学习者的反馈校准**（推荐）。
- **决定（提议）**：
  - **新词清单**：agent 为每节列出"对这个学习者来说是新的"术语和命令，每个配一句话解释。课程页里新词带下划线，点开看解释，旁边两个按钮：「有用，我确实不懂」👍 /「我早就知道」👎。学习者还可以选中一段没被标出的词，点「这个我不懂」——这是预测器漏掉的。
  - **环境强制**：讲解里出现的命令（反引号里的第一个词）如果不在"已知词表"里、也没有列进新词清单，`submit` 退回。每节新词不超过 5 个（工作记忆一次大约只能处理 4 个左右的新东西），超了就要拆节。
  - **已知词表**：从事件算出来，不手写。点过👎的词、做对了检查点的小节里的新词，都算"已知"。下次生成课程时 agent 拿到最新的已知词表，所以同一个单元重新生成，预测负荷会随着水平变化。
  - **预测负荷** = 这一节的新词数 + 新语法数，按分钟数折算，程序算，分低 / 中 / 高三档。
  - **实际负荷**：做完检查点后问一句"这一节费不费劲？"1-5 分（参考教育心理学里常用的 Paas 心智努力量表的简化版），一次点击。
- **怎么验证**：学完一个单元后看两组数：新词预测的准确率（👍 ÷（👍+👎））和漏报数（「这个我不懂」的次数）；预测负荷和自评负荷是否同向（预测"高"的节，自评也更高）。
- **实现（2026-09-25）**：新词 = 知识图的节点（D-020）。环境检查：每节新词 ≤ 5（已掌握的不算）；动手命令和讲解里 ≥2 个词的行内代码，第一个词必须是已知或已声明的命令。页面上新词带下划线，点开有 👍/👎；选中任意文字可以点「这个我不懂」（漏报）；整节通过后问 1-5 的费劲程度。预测负荷按当前的已知词表实时重算。

## D-018 课程页里可以提问，问题记进学习画像 · 提议 · 2026-09-25

- **问题**：遇到不懂的，现在只能去外面的 AI 问，问了什么没有记录，这是最直接的"哪里没讲清"的信号（F-028）。
- **证据**：F-028
- **考虑过**：
  1. 只提供一个"记下我问了什么"的框，粘贴外部 AI 的问答。——要多一步，多半不会贴。
  2. **课程页每节有一个提问框，用助教 agent 同一套环境回答**（推荐）：它看得到这一节的讲解、学习者画像和练习场当前的状态，回答只能引用打开过的页面（D-009 的规则不变）。外部 AI 问的，可以用方案 1 的框补录。
- **决定（提议）**：新事件 `question`（问题、所在小节、选中的文字、回答摘要）。问题里提到、但新词清单没列的词，自动算成预测器的一次漏报（D-017）。`python study.py weak` 的输出里加"最近问过的问题"，出题时参考。
- **依赖**：需要服务器调模型（用 `local.env` 里已有的 key），比 D-013~D-016 复杂，建议放在第二批做。
- **怎么验证**：一个单元学完，问题数、问题集中在哪几节，和 D-017 自评负荷高的节是否重合。

## D-019 课程评测报告：每个预测都对上一个实际值 · 接受 · 2026-09-25

- **问题**：现在对 agent 的评测只看"写得好不好"（评分模型打分），不看"学习者用起来怎么样"。学习者要求把预测和实际对上（F-028）。
- **证据**：F-028、F-029
- **决定（提议）**：`python study.py course-eval <单元>` 从事件日志算出一张表，每一行是一对"预测 vs 实际"：
  | 预测 | 实际 | 来源 |
  |---|---|---|
  | 每节计划分钟数 | 会话时间 | D-016 |
  | 预测负荷（低/中/高） | 自评 1-5 | D-017 |
  | 新词清单 | 👍 / 👎 / 漏报 / 提问 | D-017、D-018 |
  | 检查点难度 | 第一次就做对的比例、尝试次数 | D-013 |
  这份报告和评分模型的分一起写进 agent 运行记录。重新生成第二版 Shell 课程后，拿第一版的实际数据对比两版的预测，改 prompt 时一次只改一处（agents/README.md 的纪律不变）。
- **怎么验证**：学完 Shell 单元能出一份完整报告，并且能从报告里指出"下一版 prompt 该改哪一处"。
- **实现（2026-09-25）**：`studykit/course_eval.py`，`study.py course-eval <单元> [--plan] [--write]`：每节一行（计划/实际分钟、预测负荷/自评、新词点开/👍/👎/漏报、检查点首次对/尝试/最高提示），汇总用时比、新词准确率、首次通过率（目标 60–85%）、预测负荷与自评的秩相关，并按规则给出"下一版 prompt 可以改哪里"。

## D-020 学习者模型：一张知识图 + 一份证据，薄弱点和进度都是投影 · 接受 · 2026-09-25

> 学习者拍板（2026-09-25）：接受，和 D-017 一起做；先修边由助教 agent 生成课程时提议、导师审阅。

- **问题**：学习者的情况散在四处，各说各的：`learner.md`（手写的散文，"glob/sed 跟不上"写在这里）、`syllabus.yaml`（概念清单，没有前后依赖）、`attempts.jsonl`（答题证据）、D-017 要加的"已知词表"。
  课程一多，agent 要么全读（读不下），要么不读（不个性化）；薄弱点是散文，没法按课查、没法判断相关性（F-031）。
- **证据**：F-031；F-018（薄弱点只能写成散文）；D-017 里"已知词表"会成为第五个来源。
- **考虑过**：
  1. 把 learner.md 改成一张薄弱点表（每行：薄弱点、描述、所属课）。——还是手写的状态，会和答题证据打架；薄弱点之间没有关系，查不出"相关的"。
  2. SQLite 数据库。——查询方便，但 agent 和人都不好直接读、git 里看不出改了什么。可以以后作为**派生的索引**加上，不作为事实来源。
  3. **知识图（节点 + 先修边，按学科分文件）+ 只追加的证据；薄弱点、进度、已知词表、知识树都由程序算出来；agent 通过命令分级查询**（推荐）。
- **决定（提议）**：
  - **三层数据，只有前两层是事实来源**：
    | 层 | 是什么 | 存哪 | 谁写 |
    |---|---|---|---|
    | 知识图 | 节点（id、标题、一句话描述、类型：概念 / 术语命令 / 技能）+ `requires` 先修边 + 由哪些单元教 | `knowledge/<学科>.yaml`，一个学科一个文件 | 导师、助教 agent（生成课程时新增术语节点），学习者可改 |
    | 证据 | 答题、检查点、新词👍👎、提问、导师观察（新：`observation`，把"glob/sed 跟不上"这类话记到具体节点上） | 现有的 `attempts.jsonl`、`study_log.jsonl`，只追加 | 程序、导师 |
    | 投影 | 每个节点的状态（没学 / 在学 / 薄弱 / 掌握 / 需复习）+ 理由；薄弱点清单；已知词表（D-017）；知识树点亮；`progress.md` | 不存，随时算 | 只由程序生成 |
  - **薄弱点不再手写**：它是"状态 = 薄弱"的节点，描述 = 节点描述 + 最近 3 条证据（哪道题错了、哪句话没跟上）。每条薄弱点挂在一个节点上，证据只追加，所以不会互相覆盖；同一个节点上矛盾的证据按时间和掌握度规则（D-003）裁决。
  - **agent 分级按需加载**（命令就是查询接口，存储以后换成 SQLite 也不影响 agent）：
    | 级别 | 命令 | 给什么 | 大小 |
    |---|---|---|---|
    | 0 | `study.py kg summary` | 每个学科：掌握 / 薄弱 / 没学的数量，前 5 个薄弱点的标题 | 几十行，永远不随课程数增长太多 |
    | 1 | `study.py kg related --unit <单元>` | 这个单元教的节点 + 往上两层先修节点里**薄弱或没学**的，只给 id 和标题 | 和单元相关，不和总课程数相关 |
    | 2 | `study.py kg show <节点>` | 描述、先修的状态、全部证据 | 一个节点 |
    助教 agent 的简报用第 1 级代替整份 learner.md；需要详情时导师再查第 2 级。
  - **learner.md 保留，但只写稳定的事实**：身份、电脑环境、目标、偏好的讲法。薄弱点和起点从里面移到知识图的证据里（导师写一条 `observation`）。
  - **知识树视图**：网页新增一页，按学科画节点和先修边，状态上色（掌握 = 亮，薄弱 = 橙，没学 = 灰）；打开一个单元前能看到"它的先修里还有哪些没亮"。
  - **和 D-017 合并**：新词就是"术语命令"类型的节点；👍👎 是证据；"已知词表"是投影。D-017 不另建存储。
- **怎么验证**：① 导师出题前只跑 `kg related`，能不能拿到足够的信息（不再读整份 learner.md）；② 学完 Shell 后，薄弱点清单和学习者自己感觉的"哪里没懂"对得上；③ 知识图有 100+ 节点时，第 0、1 级输出仍然在一屏以内。
- **待定（学习者决定）**：先修边由谁建——导师手建第一版，还是让助教 agent 生成课程时顺便提议、导师审阅。
- **实现（2026-09-25）**：`knowledge/<学科>.yaml` + `studykit/knowledge.py`；证据来自答题、检查点、新词投票、导师观察（`kg observe`）；状态由最近一条有方向的证据决定，有答题记录时按 D-003 裁决。`kg summary / related / show / check`；网页 `?kg=<学科>` 画知识树。助教 agent 的简报只带 `related` 的内容和已有节点；发布时把 agent 提议的节点并入知识图。种子：导师建了 9 个 shell 节点，把 F-018 和 learner.md 里的 6 条薄弱点记成了观察。
