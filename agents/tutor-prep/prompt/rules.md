# 硬性规则

- **只写你读到的东西。** 概念、命令、练习都要能在你打开过的页面里找到出处；讲解用你自己的话写，不要大段照抄原文。
- **链接只能用你打开过的页面。** 出处在单元的 `sources` 里列一次，不要每节重复。
- 不要编造视频时间戳；`watch` 里按讲义的小节名说明对应哪一部分。
- `lab` 检查点的 `checks` 在练习场根目录执行；`solution` 是按顺序执行就能通过检查的命令，学习者跳过这一节时，环境用它把练习场补齐，让下一节能接着做。检查项要检验结果，不要检验学习者用了哪个命令。
- 做之前检查点**不能**已经通过（比如要生成的文件不能事先就在练习场里）。
- **参考做法从"学习者刚敲完本节动手步骤"的状态出发。** 环境验证时的顺序是：练习场补齐到本节开始 → 按顺序敲完动手步骤 → 检查点应该还不通过 → 执行参考做法 → 检查点通过。
  所以参考做法不能依赖"我现在在哪个分支 / 哪个目录"这类会被动手步骤改掉的状态：要回主线就明写 `git switch main`，不要写 `git switch -`（它回到的是"上一个"分支）。
- **lab 检查点在本节开始时（动手之前）必须不通过。** "撤销 / 清理 / 回到原样"这类任务的终点往往和起点一样，检查不出做没做——要么改成留下一个起点没有的痕迹（一次新提交、一份记录文件），要么换一个题目。
- 正文里不要写"分几次学完"这类由环境计算的数字（网页会按每节分钟数自己算）。
- **检查项不能被学习者"记录答案"这个动作本身改变。** 用 `git log -S`、`grep` 这类命令现算正确答案时，限定在题目针对的文件上（如 `git log -S TITLE_MAX -- app/routes/tasks.py`）；否则学习者把答案写进笔记并提交后，那次提交也会被算进去。
- **每道检查点的题干、`answer`/`accept`、提示、解析说的必须是同一件事。** 写完逐题对一遍：按题干字面意思答对的人，一定会被 `accept` 判对。
- **不要在命令里写死每个人都不一样的值。** 提交哈希取决于提交时间和作者，学习者那边的哈希和你想象的一定不同；需要哈希时让命令自己算出来（如 `git rev-list --max-parents=0 HEAD`、`git log -1 --format=%h`），或者让学习者从上一条命令的输出里抄。
- 用中文写，专有名词和命令保留英文。
- **新名词先给准确的定义，类比只作补充。** 一个术语第一次出现时，先用计算机领域里正确的说法讲清它是什么、属于哪一类东西，并把它和已经讲过的概念接上
  （例：「bash 是一个**程序**：它读入你敲的一行文本，展开其中的特殊符号，再启动别的程序并把参数交给它」——程序、参数、启动都是学习者正在建模的词）。
  学习者此时在给「程序、执行、参数、管道」这些东西建模型，跳出这套语义的比喻（秘书、传纸条、快递员）会打断建模，**不要用比喻代替定义**。
  确实需要类比时，放在定义之后，明确说「打个比方」，并指出比喻在哪里不成立。`terms` 里的 explain 也是定义，不是比喻。
- 每节的 `goal` 和整体的 `outcomes` 写成可检验的行为（"能用管道把 A 的输出交给 B"），不写"理解了 XX"。
